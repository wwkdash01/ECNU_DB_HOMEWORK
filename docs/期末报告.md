# 面向真实业务库的 Text2SQL：one-shot 与 Agent 闭环的对照研究

> **选题**：《数据库前沿技术》期末考核 A 卷　**选题方向**：方向 4（AI4DB）——Text2SQL / Database Agent
> **数据集**：BIRD Mini-Dev V1（SQLite）——500 题 / 11 库 / 75 表
> **模型**：`deepseek-flash`（DeepSeek-V4.1-Flash），**冻结 API、不训练、不本地部署**
> **代码**：`db_agent/` 包，入口 `python -m db_agent <子命令>`

---

## 1. 问题定义与应用背景

### 1.1 已知问题

**在真实业务数据库上，把自然语言问题自动翻译成结果正确的 SQL**（Text2SQL）。
评测集 BIRD Mini-Dev 的库不是教学用的单表玩具：11 个库、75 张表，题目横跨赛事统计
（`formula_1`）、医疗检验（`thrombosis_prediction`）、金融卡业务（`debit_card_specializing`）等，
需要多表连接、聚合、子查询与业务口径理解。

### 1.2 传统方法局限性

| 方案 | 局限 |
| --- | --- |
| 规则 / 模板 | 只能覆盖固定问法，无法处理开放表述与库结构变化 |
| 传统 Seq2Seq（如 IRNet 类） | 依赖大规模标注语料，且**生成时看不到执行结果**，无法自我纠正 |
| 单次 LLM 调用（one-shot） | 本任务实测可跑出 57.80%，但存在**系统性错误模式**：模型语义理解正确，却在输出形态上多带"佐证列"，被集合比较直接判错（§5.3） |

### 1.3 核心性能指标

A 卷要求明确至少两个指标。本项目选定：

| 指标 | 定义 | 为什么选它 |
| --- | --- | --- |
| **EX（执行准确率）** | `set(pred)==set(gold)`，官方 `evaluate_ex` 口径 | 主指标，唯一衡量"答对没有"的量 |
| **Latency P50 / P95** | 端到端每题耗时（含 LLM 调用与 SQL 执行） | 长尾敏感，P95 才能暴露 agent 的放大效应 |
| **QET（Query Execution Time）** | 仅最终 SQL 在库上的执行耗时，**统一重测** | 与 Latency 分离，才能把"模型慢"和"库慢"拆开 |
| **单题 token 成本** | 输入（含缓存命中）/ 输出 token | agent 类方法必须证明多花的钱换来多少提升 |

## 2. 数据库基础原理分析

本节选三个与本系统**直接耦合**的数据库基础问题。每点均给出原理、本项目如何触及、以及实测数据。

### 2.1 查询计划与索引访问路径

**原理**：SQL 是声明式语言，同样的结果集可以由全表扫描或索引查找达成，代价相差数量级。
数据库通过 `Scan`（全表扫）、`Search`（索引定位）、`TEMP B-TREE`（排序/临时表）、
`COVERING INDEX`（索引覆盖，免回表）等访问路径执行查询。SQLite 仅有 B-tree 索引，无原生 Hash。

**实测（可解析题数 / 占比）**：

| 组 | 可解析 | 含 SCAN | 含 SEARCH | 含 TEMP B-TREE | 含 COVERING INDEX | 含子查询 |
| --- | --- | --- | --- | --- | --- | --- |
| O1 | 491 | 473 (96.3%) | 379 (77.2%) | 190 (38.7%) | 34 (6.9%) | 81 (16.5%) |
| O3 | 495 | 483 (97.6%) | 382 (77.2%) | 195 (39.4%) | 32 (6.5%) | 83 (16.8%) |
| **A1** | 500 | 480 (**96.0%**) | 373 (74.6%) | 214 (**42.8%**) | 33 (6.6%) | 83 (16.6%) |

**分析**：三组的计划画像几乎一致，且**96% 的正确答案里都含全表扫描**。
这一缺陷主要由于数据集体量过小，索引为非必要优化导致。这一现象指明了一个结论：
**EX 的提升完全没有伴随计划质量的提升**。A1 的 TEMP B-TREE 占比反而从 38.7% 升到 42.8%，
即 agent 更频繁地写出了需要排序/临时表的查询。

代价侧能印证：QET 的 **P50 只有 0.55~0.66 ms，而 P95 高达 43.8~58.4 ms**（§4.2），
近 **80~90 倍**的长尾差异正是由访问路径与结果集规模决定的，而不是由模型性能决定。
**结论：本任务上 EX 与查询计划质量是解耦的，把 EX 当唯一的数据库侧健康指标会漏掉计划退化。**

### 2.2 Cardinality Estimation 与结果集等价性：投票判据本身就是一次基数比较

**原理**：Cardinality Estimation（基数估计）是优化器选择连接顺序与访问路径的依据——
它估计"这一步会产出多少行"。估错的代价是选错计划。
在应用层，"结果集有多大、长什么样"同样是判断语义是否等价的核心信息。

**本项目如何触及**：O3 组的投票**不比较 SQL 文本，而是比较执行结果集的哈希**。
这等于把判据从"语法相似"上移到"基数 + 内容等价"——**不问你写的 SQL 像不像，只问你算出来的
东西一样不一样**。这是 cardinality/结果集思想在应用层的直接落地。

**实测（O3 机制体检，`score.py:o3_mechanism_health`）**：

| 体检项 | 值 | 含义 |
| --- | --- | --- |
| 静态层（thinking 关闭 / T=0.7 / K=3） | **全 PASS** | 机制前提成立，不是"采样退化成 O1"的静默失败 |
| 三次候选 SQL 全同 | 115 (23.0%) | 采样未发散 |
| **执行结果集簇数 = 1** | **380 (76.0%)** | **三候选答案完全相同 → 投票是空操作** |
| 结果集簇数 = 2 / 3 | 102 / 13 | 只有 **115 题 (23%)** 存在分歧 |

**分析**：以"结果集"为等价类来判定候选一致性，在这个 workload 上的**分辨率只有 23%**——
76% 的题目上三个采样候选的执行结果完全一样，投票在数学上不可能产生任何影响。
**结论：结果集等价是一个高精度但低覆盖的判据**；
它的信息量主要取决于 workload 的多样性，与候选数量关联较低。

### 2.3 执行代价、结果集规模与回灌：用一次真实执行换基数估计

**原理**：数据库的 Buffer/Cache 决定热点数据命中率；结果集规模决定网络与内存代价。
在 agent 场景中，**把执行结果回灌给模型**本身是一次"用真实执行换估计"的操作，
但需要限制模型的回灌行为，防止上下文失控增长。

**项目方案**：通过A1 的 `run_sql` 工具（`experiment/tools.py`）进行三重县志：

| 限制 | 值 | 数据库意义 |
| --- | --- | --- |
| 返回行数上限 | `RESULT_ROW_LIMIT = 100` | 避免大结果集拖垮上下文 |
| 单条 SQL 执行超时 | `QUERY_TIMEOUT_SEC = 5` | 防止 agent 被慢查询挂死 |
| 工具返回值截断 | `TOOL_OUTPUT_MAX_CHARS = 2000` | 只回灌"**N 行，M 列（列名…）**+ 3 行预览" |

## 3. 系统设计与实现

### 3.1 总体架构与三层分工

```
┌─────────────────────────────────────────────────────────────┐
│  LLM 层   deepseek-flash（冻结，thinking 显式关闭）           │
│   职责：生成 SQL 文本；决策下一次工具调用                      │
│   绝不参与：判分、答案对错的获知                               │
├─────────────────────────────────────────────────────────────┤
│  应用层   db_agent/ 包                                       │
│   core/        数据加载 build_context / 只读连接 / API 出口    │
│   experiment/  run_oneshot · run_selfconsistency · run_agent │
│   evaluation/  score(官方判分) · paired(McNemar) · analyze    │
│   ops/  tui/   数据抓取、三段验收、复刻流程 TUI                 │
│   职责：结果集哈希聚类投票、配对检验、指标计算、prompt 组装      │
├─────────────────────────────────────────────────────────────┤
│  数据库层  SQLite（11 库 / 75 表，只读连接）                   │
│   职责：SQL 解析、查询计划、执行、超时、结果集返回              │
│   不做：任何语义判断                                           │
└─────────────────────────────────────────────────────────────┘
```

| 功能 | 实现来源 |
| --- | --- |
| SQL 生成、工具调用决策 | **LLM** |
| SQL 解析与执行、查询计划、结果集产出 | **数据库（SQLite）** |
| schema 拼装进 prompt（schema linking） | 应用层 |
| 结果集哈希聚类投票（O3）、迭代控制（A1） | 应用层 |
| EX 判分、列级召回、幻觉率、McNemar | 应用层（复用官方脚本） |
| 温度、`MAX_STEPS`、沙箱参数 | 应用层（`config.py` 单一事实源） |

### 3.2 数据流程

```
mini_dev_sqlite.json (500 题：question / evidence / db_id / difficulty)
        │
        ▼
build_context()  ──►  组装 prompt：DDL(schema) + evidence + question
        │              （O 组与 A 组【逐字共用】同一入口 —— 「起点冻结」）
        ▼
   ┌────┴─────────────────────────────┐
   │ O1: 单次调用                      │
   │ O3: T=0.7 采样 K=3 → 各自执行      │
   │     → 结果集哈希聚类 → 多数簇投票   │
   │ A1: 循环 MAX_STEPS=10             │
   │     run_sql 回灌(行数/列名/列数/3行)│
   │     submit_answer 提交并终止       │
   └────┬─────────────────────────────┘
        ▼
  final_sql  ──►  score.py：官方 execute_sql + calculate_ex
                  ──►  results/<group>_scored.jsonl
                  ──►  paired.py（McNemar 精确检验 + 分层 + 翻盘题）

```

### 3.4 存储与索引设计

**本项目不设计存储与索引，而是直接复用 BIRD 提供的物理库**

| 项 | 做法 | 理由 |
| --- | --- | --- |
| 物理文件 | 沿用随数据集分发的 11 个 `.sqlite` | 属评测口径的一部分，改动会使 EX 不可比 |
| 索引 | **不新建、不删除** | 数据集未提供索引定义，评测以原始库为准 |
| 表结构 | **不改 DDL** | 同上 |
| 连接方式 | **只读** `file:...?mode=ro` | 防止实验过程污染数据 |
| 特例 | `card_games` 为 WAL 模式，只读打不开 → 回退 `immutable=1` | 存储引擎特性反向影响应用设计 |


### 3.5 查询流程

从最终答案到判分的**执行路径**：

```
final_sql
   │
   ├─► core/db.py: execute()             ← 唯一执行入口
   │     · 只读连接按库缓存复用
   │     · fetchmany(100+1)  → RESULT_ROW_LIMIT=100（不遍历完整结果集）
   │     · 单条超时 QUERY_TIMEOUT_SEC = 5 s
   │     · 记录 QET（执行耗时）
   │
   ├─► 判分路径（离线，score.py）
   │     · 官方 execute_sql(pred, gold, db_path, "SQLite", calculate_ex)
   │     · func_timeout(30 s) 包裹；异常归类为 timeout / exec_error
   │     · calculate_ex  =  set(pred_res) == set(gold_res)
   │
   └─► agent 路径（在线，仅 A1）
         · 复用同一 execute()，但**只回灌**「N 行，M 列（列名…）」+ 3 行预览
         · 截断至 TOOL_OUTPUT_MAX_CHARS = 2000
         · 报错原样回灌，模型据此决定下一轮
```

### 3.6 三组的核心算法

| 组 | 算法 | 温度 | 工具 | 关键实现 |
| --- | --- | --- | --- | --- |
| `O1` | one-shot ×1 | 0.0 | — | `methods.run_oneshot` |
| `O3` | 采样 ×3 + **按执行结果集哈希聚类投票** | 0.7 | — | `methods.run_selfconsistency` |
| `A1` | agent 循环 + **输出形态自检** + `submit_answer` 终止 | 0.0 | `run_sql` | `methods.run_agent` |


### 3.7 关键实现要点

| 问题 | 后果 | 处理 |
| --- | --- | --- |
| 模型ReAct循环过长 | `final_sql` 采集失败 | 新增 `submit_answer` 终止动作 |
| 工具禁用导致模型输出畸形 | 45% 的 `final_sql` 不可执行 | `strip_tool_syntax()` + 取最后一条查询 |
| ReAct循环轮次不足 | 11/11 次提交都压在第 3 轮，9/20 从未提交 | 3 → 10，改定位为**安全护栏**（模型提交即停） |
| `question_id` 包含重复值 | 断点续跑漏跑 2 题，只得 498 条 | 改用 `qidx`（0..499 下标） |

## 4. 对照实验

### 4.1 实验方法

**n = 500，同一批题同一批次执行完毕后，逐题配对比较。**

**关于「Baseline」的口径说明。**
本项目的`O1`（plain LLM Text2SQL）与 `A1`（execution-guided）**逐字对应该示例的两侧**，
故 `O1` 即本子方向下的合法 Baseline。

### 4.2 Baseline 与主结果

**Baseline = `O1`（one-shot ×1）**，这是最朴素的 LLM 方案，也是"是否值得引入复杂度"的判据。

| 指标 | O1（Baseline） | O3 | **A1** |
| --- | --- | --- | --- |
| **EX** | 57.80% | 59.40% | **64.40%** |
| 简单（n=148） | 72.30% | 71.62% | **79.05%** |
| 中等（n=250） | 54.40% | 57.20% | **60.80%** |
| 困难（n=102） | 45.10% | 47.06% | **51.96%** |
| 列级召回 | 90.81% | 90.61% | 89.02% |
| 幻觉率 | 0.78% | 0.97% | **0.68%** |
| Latency P50 | 0.67 s | 2.02 s | 2.60 s |
| Latency P95 | 0.98 s | 2.76 s | **6.95 s** |
| QET P50 / P95 | 0.66 / 58.39 ms | 0.55 / 43.81 ms | 0.55 / 44.92 ms |
| `exec_error` | 9 | 5 | **0** |
| `timeout` | 2 | 2 | 2 |
| 调用 / 题 | 1.00 | 3.00 | 3.57 |
| 输出 token | 28,628 | 85,930 | 225,815 |

### 4.3 配对检验（McNemar 精确检验）

净翻转 = 后组 − 前组；「不一致对」才是携带处理效应信息的题目。

| 对比（后 − 前） | 净变化 | 仅前组对 | 仅后组对 | 不一致对 | p 值 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **O3 − O1** | +8 题（+1.60pt） | 5 | 13 | **18** | **0.0963** | **不显著** |
| **A1 − O1** | **+33 题（+6.60pt）** | 29 | 62 | 91 | **0.0007** | **显著** |
| **A1 − O3** | **+25 题（+5.00pt）** | 34 | 59 | 93 | **0.0124** | **显著** |

三条结论：
1. **A1 相对 O1 显著更优**：+6.60pt，p = 0.0007。
2. **O3 相对 O1 不显著**：+1.60pt，p = 0.0963，且**不一致对只有 18 题**——
   `paired.py` 会自行警告：这种规模下即便 p<0.05 也很脆弱。
3. **O3 显著劣于 A1**：O3 相对 A1 在**三档难度上全部为负**
   （simple −7.4pt / moderate −3.6pt / challenging −4.9pt）。

### 4.4 消融与敏感性实验

**项目方案**：利用 workload 的**固有分层**做敏感性分析，自变量是「查询复杂度 / Workload 结构」：

| 分层维度 | 分层依据 | 数据来源 |
| --- | --- | --- |
| **难度分层**（simple/moderate/challenging） | BIRD 官方标注，代表查询复杂度 | §4.2 表 |
| **gold 所需表数**（1/2/3/4–5 表） | 代表连接复杂度 | §5.3 |
| **EXPLAIN 访问路径分桶** | 代表物理执行复杂度 | §2.1 |

基本结论：**难度分层给出的差异很小（各档 Δpt 都在 ±7pt 内），而按表数分层给出的差异极大**（1 表 EX 81.4% → 3 表 EX 47.1%）。


### 4.5 代价对照

| | O1 | O3 | A1 |
| --- | --- | --- | --- |
| 调用次数（总计） | 500 | 1,500 | **1,783** |
| 其中 `run_sql` / `submit_answer` | — | — | 1,768 / 497 |
| 输入 token（含缓存） | 488,730 | 1,466,190 | 3,894,598 |
| 其中缓存命中 | 393,009 | 1,179,027 | 3,522,436 |
| **缓存命中率** | 80.4% | 80.4% | **90.4%** |
| 缓存未命中输入 | 95,721 | 287,163 | 372,162 |
| 输出 token | 28,628 | 85,930 | 225,815 |

**延迟分解**（长尾归因的前提）：

| 组 | Σ总延迟 (s) | Σcall_latency | ΣQET | Σ调度开销 | 单次调用 P50 / P95 | 调用次数 |
| --- | --- | --- | --- | --- | --- | --- |
| O1 | 344 | 344 | 0 | 0 | 0.67 / 0.98 | 500 |
| O3 | 1058 | 1014 | 0 | 44 | 0.66 / 0.97 | 1500 |
| A1 | 1558 | 1513 | 19 | 27 | 0.82 / 1.25 | 1783 |

**基本结论**：A1 的端到端 P95 是 O1 的 7 倍（6.95 s vs 0.98 s），但**单次调用 P95 仅从 0.98 s 升到 1.25 s**。
可见长尾主要来自**轮数变多**（调用次数 500 → 1783），而非单次调用变慢。因此agent 放大了 API 固有的长尾，而不是本身性能原因。

## 5. 结果分析与失败案例

### 5.1 失败案例：O3 未显著优于基准，且显著劣于 A1

| 结论 | 数据 |
| --- | --- |
| O3 相对 O1 的提升 | +1.60pt，**p = 0.0963，不显著** |
| 不一致对规模 | **仅 18 题**（`paired.py` 自行警告其脆弱性） |
| O3 相对 A1 | **−5.00pt，p = 0.0124，显著劣于** |

### 5.2 机制归因

| 指标 | 值 | 含义 |
| --- | --- | --- |
| 三次候选 **SQL 全同** | 115 (23.0%) | 采样根本没发散 |
| 候选有差异 | 385 (77.0%) | 采样确实在发散 |
| **执行结果集簇数 = 1** | **380 (76.0%)** | **三候选答案完全相同 → 投票是空操作** |
| 结果集簇数 = 2 / 3 | 102 / 13 | 只有 **115 题（23%）** 存在分歧 |
| 候选全失败退回 | 5 题 | 采集兜底，须披露 |
| 候选执行结果 | ok 1462 / timeout 4 / OperationalError 34 | **2.5% 的候选未跑出结果** |

**机制**：

| 考查维度 | 本项目的位置 |
| --- | --- |
| **Workload Dependency** | 投票价值高度依赖 workload 的"多解性"。BIRD 多数问题有唯一正确答案且输出形态唯一 |
| **Data Distribution** | 见 §5.3——增益随"所需连接表数"急剧衰减：1 表 EX 81.4% → 3 表 47.1%，且 A1 在 3 表题上零改进 |
| **Model Generalization** | 即便 T=0.7，`deepseek-flash` 关闭思考模式后采样多样性有限（23% 的题连 SQL 文本都全同 |
| **Cost Trade-off** | 见 §4.5 / §4.7——O3 花 3 倍 token 换不显著的 +1.60pt；A1 花 8 倍 token 换 +6.60pt；A1 的边际收益在 k=5 后迅速衰减 |
| **Tail Latency** | 见 §4.5 延迟分解——端到端 P95 涨 7 倍，但单次调用 P95 仅 0.98→1.25 s，长尾现象主要来自ReAct轮数|

### 5.3 具体失败案例

数据目录 `results/repro3/` 完整保存了纠正清单。

- **q70**（simple / `student_club`，A1 用了 2 轮）
  - 问：State the category of events were held at MU 215.
  - **A1 SQL**：`SELECT DISTINCT type FROM event WHERE location = 'MU 215'`
  - gold：`SELECT DISTINCT T2.category FROM event AS T1 INNER JOIN budget AS T2 ON T1.event_id = T2.link_to_event WHERE T1.location = 'MU 215'`

    A1 执行成功（`type` 列存在），执行反馈**无法暴露这个语义错误**，与 §5.4 一致。

- **q105**（moderate / `thrombosis_prediction`，A1 用了 6 轮）

  - gold：`INNER JOIN Laboratory` 后 `WHERE ... AND T1.SEX = 'M'`

**纠正**的代表案例（说明形态自检的直接效果）：

## 6. 前沿性与局限性分析

### 6.1 对比论文

**论文 A：DAIL-SQL（PVLDB 2024）**
Gao et al., *Text-to-SQL Empowered by Large Language Models: A Benchmark Evaluation*,
**PVLDB 17(5): 1132–1145, 2024**. 系统评测了 LLM 在 Text2SQL 上的 prompt 工程路线，
核心贡献在 **schema 表示**（DDL 压缩、M-Schema）与**示例选择**（DAIL Selection）。
代表"不训练、纯 prompt 侧优化"这一路线。

**论文 B：Reward-SQL（SIGMOD 2026）**
Zhang et al., *Reward-SQL: Boosting Text-to-SQL via Stepwise Execution-Aware Reasoning and
Process-Supervised Rewards*, **PACMMOD 4(3), Article 228（SIGMOD）, 2026**,
DOI `10.1145/3802105`（arXiv:2505.04671）。提出 **CoCTE** 分治式执行感知推理：
把复杂查询拆成一系列**可执行**的 CTE，每步**即时执行**以获取步骤级反馈；
再用**过程奖励（PRM）+ RL** 训练。BIRD 上以 **8B 模型达 70.3% EX**，
相比 Qwen3-8B GRPO 基线把表选择错误降低 42.6%、GROUP BY 错误降低 82.4%。

### 6.2 项目现状

**（1）项目成果**

| 参照 | Mini-Dev / BIRD 上的 EX |
| --- | --- |
| 官方 Mini-Dev 基线 gpt-4（SQLite EX） | 47.80 |
| 官方 Mini-Dev 基线 TA + gpt-4-turbo | 58.00 |
| 官方 Mini-Dev 基线 TA + gpt-4o | **63.00** |
| **本项目 O1（Baseline）** | **57.80** |
| **本项目 A1** | **64.40** |
| Reward-SQL（8B，RL 精调，BIRD） | **70.30** |
| XiYan-SQL（BIRD dev，需微调） | 73.34 |

**结论**：本项目用**冻结的 API 模型、零训练**，A1 达到 64.40%，
略高于官方 Mini-Dev 最强基线 TA+gpt-4o（63.00）。但与需要**微调生成器 + 微调选择模型/RL**
的 SOTA 系统（70.3~73.3）仍有 **6~9pt** 差距——**这 6~9pt 差距基本等于"训练"的价值**。

**（2）前沿差距**

| 维度 | 本项目 | DAIL-SQL / Reward-SQL |
| --- | --- | --- |
| 模型 | 冻结 API，零训练 | 微调生成器 + 选择模型 / RL 训练 |
| 反馈使用 | 只把"行数/列名/列数"回灌，**且模型无法验证对错** | 步骤级可执行反馈 + **过程奖励**做信用分配 |
| 候选重排 | **无选择模型**，O3 直接多数投票 | 专门的选择模型 / PRM 打分 |
| Schema 表示 | raw DDL 直塞 prompt，无 schema linking | M-Schema + schema linking（业证 +4pt 量级） |
| 样本量 | 500 题 / 单模型 / 单库族（SQLite） | 全量 BIRD + 多方言 |

**（3）结论局限性？**

- **O3 的"零增益"难以推广到有 RL 精调的场景**。本项目的 O3 是
  "无选择模型 + 冻结采样"的投票，Reward-SQL 这一类工作恰恰证明：
  加上**过程奖励与选择模型**后，多候选的价值可以被释放出来。
- **SQLite-only 的局限性**：SQLite 只有 B-tree、无原生 Hash 索引，
  故 A 卷清单中「B+树 vs Hash」的对比在本项目**无法完成**。
- **单模型单数据集**：所有结论只对 `deepseek-flash` + Mini-Dev 成立。

**（4）未来方向**

按证据强度排序：

1. **多表 schema linking**（打 §5.3 中 37.6% 的表选错、3 表题 47.1% 的塌陷）。
   本项目曾实现一版"表连通性"工具但**效果 ≈ 0**：20 个被漏掉的表被工具正确找出，
   **只有 2 个被采纳**。因此真正要回答的不是"怎么找表"，而是
   **"模型看得见候选表，却不肯改自己的表选择"**——这需要一个把 schema 证据变成
   强制约束的机制，而不是再给一个提示。
2. **执行反馈驱动的候选重排**（打 §5.2 中 23% 的分歧题、§5.4 中"重写=重新掷骰子"）。
   让执行信号参与**选择**而非仅参与**生成**，是 O3 未能兑现但 Reward-SQL 已证明可行的方向。
3. **预期行数量级自检**（打 44 条仅行数错）。与已生效的形态自检同构，改动最小；
   但前提是"问题本身规定了行数量级"，该前提**不自动成立**，需先验证覆盖率。

```bash
P=~/.conda/envs/db_agent/bin/python
cd <仓库根>
$P -m db_agent check        # 打印 9 步状态表；另有 check 的非交互说明
```

**逐条手动等价命令**：

| TUI 步骤 | 手动等价命令 | 产物 / 状态判据 |
| --- | --- | --- |
| 1 环境 | （无需命令，`check` 会一并报出） | 5 个直接依赖齐全 |
| 2 密钥 | `$P -m db_agent set-key`（密钥从 stdin 读入，见 `README.md`） | `.env` 可读到密钥（权限 600） |
| 3 Gate 0 | `$P -m db_agent gate 0` | `results/env.json`　**（花钱：2 次真实调用）** |
| 4 数据 | `$P -m db_agent fetch` | `data/dev_databases/`（11 库） |
| 5 Gate 1 | `$P -m db_agent gate 1` | 离线，约 15 s |
| 6 Gate 2 | `$P -m db_agent gate 2 --offline` | 离线；去掉 `--offline` 会另跑 1 题真实调用 |
| 7 跑组 | `$P -m db_agent run --group O1`（O3 / A1 同法） | `results/<group>.jsonl`　**（花钱：唯一的大额项）** |
| 8 判分 | `$P -m db_agent score --group O1`（O3 / A1 同法） | `results/<group>_scored.jsonl`，离线 |
| 9 配对 / 分析 | `$P -m db_agent pair <A_scored> <B_scored>`<br>`$P -m db_agent analyze --out results/analyze.md` | `pair` 输出到 stdout（TUI 版落盘为 `results/.tui/paired_*.txt`）；`results/analyze.md`，均离线 |

**完整串起来**：

```bash
# 数据与密钥验收
$P -m db_agent gate 1
$P -m db_agent gate 0

# 三组试验（加 --concurrency 20 提速；单组全量约 2 分钟）
for G in O1 O3 A1; do $P -m db_agent run --group $G --concurrency 20; done

# 判分 + 配对比较 + 离线分析
for G in O1 O3 A1; do $P -m db_agent score --group $G; done
$P -m db_agent pair results/repro3/O1_scored.jsonl results/repro3/A1_scored.jsonl
$P -m db_agent analyze --out results/analyze.md
```

**手动复现的三个注意点**：

1. **`pair` 必须从仓库根、带 `results/repro3/` 前缀调用**。`pair` 的参数解析会先找
   `<仓库>/results/`，同名文件会被静默遮蔽——若读到另一批次不会报错，只会给出错误结论。
   **自检**：第一条应输出 `O1 EX = 289/500 = 57.80%` 与 `A1 EX = 322/500 = 64.40%`；
   若看到 `58.40% / 63.40%`，说明读错了批次。
2. **`score` 的 `--out` 是输入文件名，不是输出路径**（输出固定为 `<名字>_scored.jsonl`）。
   正常复现**不要传它**，直接 `score --group X`。
3. **冒烟测试要加 `--out`**：`run --group A1 --limit 20` 若不加 `--out`，会去读
   `<group>.jsonl` 的断点记录；该文件已是全量 500 条时，前 20 题会被判"已完成"从而**一题不跑**。
   正确写法：`run --group A1 --limit 20 --out A1_smoke.jsonl`（写独立文件名，不污染全量断点）。

## 附录 A · LLM 使用规范说明

### A.1 哪些环节使用了 LLM

| 环节 | 是否使用 LLM | 说明 |
| --- | --- | --- |
| **SQL 生成** | ✅ **是** | 三组（O1/O3/A1）的最终答案 `final_sql` **全部**由 `deepseek-flash` 生成 |
| **工具调用决策**（A1） | ✅ 是 | 模型自行决定何时 `run_sql`、何时 `submit_answer` |
| **SQL 执行** | ❌ 否 | 由 SQLite 执行 |
| **判分（EX / 列级召回 / 幻觉率）** | ❌ **否** | 由官方 `execute_sql` + `calculate_ex` 与 `sqlglot` 解析完成 |
| **配对检验 / 分层统计** | ❌ 否 | `paired.py` 的 McNemar 精确检验 |


### A.2 LLM 生成的关键 SQL 如何验证

1. **强制可执行**：`submit_answer` 是唯一终止动作，**提交物必须能被 SQLite 执行**，
   否则被拒绝——从源头排除了"看起来对但跑不通"的答案。
2. **统一判分**：每条 `final_sql` 由官方 `execute_sql` 在真实库上执行，
   用 `calculate_ex` 做 `set(pred)==set(gold)` 比较。
3. **静态解析**：列级召回与幻觉率由 `sqlglot`（sqlite 方言）解析后与 gold 对比，
   不经模型判断。
4. **多层验收**：`gate 0/1/2` 三段脚本分别验收密钥与 tool-calling、数据与起点、
   代码与埋点（含 `AGENT_SYSTEM` 冻结守卫，防止 prompt 被无意改动）。

### A.3 发现的 LLM 错误

| 错误 | 表现 | 处理 |
| --- | --- | --- |
| **不主动终止** | 始终不给出最终答案，`final_sql` 采集失败 | 新增 `submit_answer` 终止动作 |
| **输出畸形调用语法** | 工具被禁用后，仍把调用语法当纯文本输出 | `strip_tool_syntax()`；**45% 的 `final_sql` 曾不可执行** |
| **特殊标记泄漏** | 模型特殊标记混进 `final_sql` → 语法错 | 已处理并记录 |
| **多带"佐证列"** | 语义正确但多返回一列 → EX 判错 | 输出形态自检（§5.5），**占改动前错误的 48.6%** |
| **幻觉** | 产出数据库中不存在的标识符 | 实测幻觉率 0.68%~0.97%（三组均低，**无区分度**） |
| **不做必要的工具调用** | 曾出现 9/20 从未提交 | `MAX_STEPS` 3 → 10 + `submit_answer` |

### A.4 如何确认实验结果不是由生成错误导致的

1. **判分与生成严格隔离**：agent **永远看不到**答案对错，仅能看到"执行成功/报错/几行几列"。
2. **判分不使用 LLM 自评**：EX 来自**真实执行 + 集合比较**，不依赖模型判断对错。
3. **同批次配对**：不以历史数字作对照。实测同配置重跑的噪声底为 ±1pt / 3~4% 翻盘（§4.6），
   而 A1 的处理效应为 +6.60pt / 18.2%——**效应是噪声的 7~11 倍**。
4. **翻盘题级交叉验证**：两次独立运行的"救回"题 Jaccard = 0.69（交集 46 题，
   是随机期望 6.3 题的 7.3 倍），说明增益作用在**同一批具体题目**上，是可复现机制。
5. **小样本假信号的教训**：本项目早期 n=30 的对照实验**三次全部给出假信号**
   （例如"表连通工具 +37pt"，实为定向抽样取到了模型本来就全对的题），
   最终均被全量 500 题推翻。**故本报告所有结论均基于全量 n=500。**
6. **兜底如实披露**：A1 的 3/500 与 O3 的 5/500 采集兜底已单列（§7.5），
   不混入方法效果。

### A.5 关于「不得把 LLM 生成的结论直接作为实验结论」

本报告遵守该条：**全部实验结论均来自可执行、可复算的数据，而非 LLM 的陈述。**

- §2~§5 的每一个数字都可追溯到 `results/repro3/` 的判分产物——由官方 `execute_sql`
  在真实 SQLite 库上**实际执行**、再经 `calculate_ex` 比较得出；或来自 `paired.py` /
  `analyze.py` 的**确定性统计**（McNemar 精确检验、分层计数、`EXPLAIN` 解析）。
- LLM 在本项目中**只生成 SQL 文本与工具决策，不产出任何结论性判断**：
  它既不知道答案对错（§A.1 与 §3.2 原则 2），也不参与判分。
- 报告中**不含任何"由 LLM 声称、而未经执行验证"的结论**。凡属推断而非实测的表述，
  均已显式标注（如 §5.1 的温度混淆项、§6.2 的不可推广性、§6.3 的局限表）。
